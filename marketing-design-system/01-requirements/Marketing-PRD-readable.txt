PRODUCT REQUIREMENTS DOCUMENT (PRD)
Arnifi Marketing Design System
Product: Arnifi Marketing Studio Version: MVP 1.0 Platform: Desktop-first Web Application Development Environment: Claude Code Design Source: Figma through MCP / API Status: Ready for MVP development, subject to Figma source inspection Purpose: Internal stakeholder demonstration and product validation

1. Executive Summary
1.1 Product Overview
Arnifi Marketing Studio is a self-service web application that enables Arnifi's internal teams to create professional, brand-consistent marketing creatives using predefined templates.
Instead of creating every LinkedIn or Instagram post manually in Figma, users select an approved template, replace its text and images, adjust individual elements, preview the output, and download the finished creative.
For the MVP, Claude Code will use the connected Figma MCP to inspect the provided Figma file, identify the 20 most suitable marketing designs, and recreate them as reusable, editable templates.
The application must preserve the original visual quality of those designs while providing a simple, beginner-friendly editing experience.
Core user journey:
Template Library → Select or Upload Template → Customize Design → Live Preview → Export
1.2 Product Vision
Enable any Arnifi marketing team member to create a professional, on-brand marketing creative within minutes, without requiring Figma knowledge or routine assistance from the design team.
1.3 Product Principles
Template-first: Users start with professionally designed layouts rather than a blank canvas.
Easy to use: Editing must be understandable to someone without design experience.
Design fidelity: Imported templates must visually resemble their Figma originals.
Flexible editing: Text, images, logos, and footers should be individually editable or movable.
Brand consistency: Default designs follow Arnifi's existing design system.
Fast output: The shortest path from template selection to export should require minimal interaction.
MVP discipline: Demonstrate the complete core workflow without building unnecessary platform features.

2. Problem Statement
2.1 Current Problem
Arnifi frequently needs marketing creatives for social media, campaigns, announcements, educational content, and business-related posts.
The current process depends heavily on designers manually editing existing posters or recreating similar layouts.
This creates several challenges:
Repeated design work for similar marketing posts.
Marketing team dependency on designers for simple copy and image updates.
Inconsistent layouts when designs are recreated manually.
Time spent searching for existing poster designs.
No centralized, self-service template creation experience.
These are the problems the MVP is intended to address. Their frequency and time impact should be validated with actual users rather than assumed.
2.2 Proposed Solution
Create a central web application containing approved Arnifi marketing templates.
Users can choose a template and update its contents without redesigning the creative.
The application's editor will handle common design adjustments while retaining the original structure and visual quality.
2.3 Expected Outcome
Reduced repetitive design work.
Faster marketing creative production.
Greater independence for non-designers.
More consistent brand presentation.
Easier reuse of existing design assets.

6. Figma Template Discovery and Selection
This is a critical part of the product.
6.1 Existing Environment
Assume the following are already available within Claude Code:
An existing project or project workspace.
Arnifi's design system and relevant implementation rules.
A Figma file link containing marketing posters.
A configured Figma MCP connection, or instructions for connecting it.
Claude Code must verify these assumptions before proceeding.
Do not recreate the design system without first inspecting the existing one.
6.2 Figma Inspection Process
Claude Code must:
Verify that the Figma MCP connection works.
Open the provided Figma file.
Inspect its pages and relevant frames.
Identify marketing posters and social media layouts.
Obtain structured layer information for suitable frames.
Capture reference screenshots.
Collect available text, assets, dimensions, styles, and layer relationships.
Build an inventory of eligible poster designs.
Use Figma MCP tools appropriate to the connected environment, including design context, metadata, screenshots, and asset downloads.
If MCP does not provide sufficient structured data, investigate the official Figma API as a development-time fallback using authorized access.
Do not assume every visible frame is an eligible template.
6.3 Template Selection Logic
From the available posters, select up to 20 of the best candidates.
Selection criteria:

25%

20%

15%
Coverage of marketing use cases
15%
The scores are selection guidelines, not a requirement for a complex AI ranking model.
Prioritize a balanced collection, based on what actually exists in the source file, such as:
Business setup posts.
Educational or informational posts.
Service promotions.
Announcements.
Campaign creatives.
Comparison layouts.
Image-led posters.
Typography-led designs.

Call-to-action posters.
Do not invent templates or source categories that are absent from the Figma file.
Avoid selecting visually identical designs solely to reach the target of 20.
If fewer than 20 suitable source designs exist, report the actual count and the reason for the shortfall.
6.4 Required Template Inventory
Before implementation, create an internal template inventory containing:

Image layer count.
Logo and footer presence.
Font families and styles.
Import complexity.

The source reference must remain traceable so any reconstructed template can be compared against its original.

7.3 Typography Rules
Preserve typography from the Figma source.
Inter and Lora are expected to be common fonts, but Claude Code must verify the actual font used by each layer.
Rules:
Do not replace every font with Inter automatically.
Retain Lora wherever it appears in the source.
Preserve font weights and hierarchy.
Load the required fonts before canvas rendering and exporting.
Detect unavailable fonts and flag them.
Use the existing project font assets or approved font sources, respecting font licensing.
7.4 Editable and Non-Editable Layer Handling
For the MVP:
Text layers must remain editable text.
Images must remain replaceable image objects.
Logos should be individually selectable where possible.
Footer elements should be separate or manageable as a group.
Supported shapes should remain editable canvas objects.
Complicated decorative effects may be rasterized individually when faithful recreation is not practical.
If a decorative effect must be flattened, flatten only the necessary layer or group, not the entire poster.
Record these limitations in the template inventory.
7.5 Asset Reliability
Download and store authorized assets within the project.
Do not depend on temporary Figma-hosted image URLs at runtime.
Every template must render after a fresh application build without requiring the Figma MCP connection.

Journey B — Upload a Personal Template
User opens the Template Library.
User clicks Upload Template.
User selects a supported file.
Application identifies the file format.
A new project opens using the imported content.
User adds or edits supported elements.
User previews the design.
User exports the result.
Important distinction:
For PNG/JPG uploads, the existing pixels are treated as an image or background. Users can add editable text, image objects, logos, and other layers over it, but cannot directly edit text baked into that image.
A native project/template JSON file produced by this application can retain individual editable layers.
Do not promise automatic layer extraction from generic flat image uploads.
Journey C — Edit an Existing Project
User reopens a locally saved project.
Previous edits are restored.
User continues making changes.
Updates are saved locally.
User exports the latest version.
Journey D — Add Templates From Figma
Development workflow for MVP; not an end-user screen.
Designer creates posters in Figma.
Claude Code accesses the Figma file through MCP.
Relevant frames are inspected and selected.
Frames are converted into structured template data.
Assets and screenshots are stored locally.
Imported templates are validated.
Approved templates appear in the web application's library.
In V2, this workflow may become an in-product Figma import and synchronization feature.

10. Detailed Functional Requirements
FR-01 — Template Library
Requirement: Users can browse and select imported templates.
Acceptance Criteria:
The gallery displays accurate previews.
Twenty selected templates are targeted for the completed MVP.
Each card opens its associated editable template.
Template dimensions remain correct.
Missing assets produce an identifiable error rather than an empty card.
FR-02 — Template Editing
Requirement: Users can edit supported individual design elements.
Acceptance Criteria:
Clicking an object selects it.
Selected objects have a visible selection indicator.
Dragging moves the object.
The properties panel reflects the selected object.
Changes appear immediately.
Original master template data is not overwritten by project edits.
FR-03 — Text Editing
Requirement: Users can modify template text without recreating the layout.
Required Behaviors:
Select text.
Update its contents using the right panel.
Move it up/down and left/right.
Change alignment.
Change font size.
Change color.
Resize the text box.
Preserve original styling by default.
Acceptance Criteria:
The text remains editable after saving/reloading.
Text updates appear immediately.
Long content is not silently clipped.
Users receive a visible indication when content overflows.
Empty text fields do not cause crashes.
FR-04 — Image Editing
Requirement: Users can replace and reposition images.
Required Behaviors:
Select an image layer.
Upload a replacement image.
Preserve the original placeholder bounds by default.
Support contain/cover behavior for common image replacements.
Adjust position or size.
Acceptance Criteria:
Image replacement does not disturb unrelated layers.
The uploaded image appears in live preview.
Export includes the correct image.
Unsupported files show an error.
FR-05 — Logo and Footer Management
Requirement: Brand elements are reusable but adjustable.
Required Behaviors:
Select logo.
Move logo.
Hide or show logo.
Remove logo from the current project.
Restore removed logo.
Move or hide footer.
Reset brand elements to original placement.
Acceptance Criteria:
Hiding an element excludes it from export.
Moving an element updates its position.
Reset restores original template coordinates.
Changes affect the current project, not all templates.
FR-06 — Layer Management
Requirement: Support basic object organization.
Required Behaviors:
Select layers from the left panel.
Visually identify the selected canvas object.
Change visibility.
Move selected elements.
Preserve stacking order.
Advanced grouping and unrestricted vector editing are not required for the MVP.
FR-07 — Undo, Redo and Reset
Requirement: Users should safely explore edits.
Acceptance Criteria:
Undo reverses the previous committed edit.
Redo reapplies it.
Drag operations are recorded as meaningful history actions rather than thousands of intermediate states.
Reset restores the current project's original template layout after confirmation.
Reset does not delete unrelated saved projects.
FR-08 — Live Preview
Requirement: Users see their modifications immediately.
Acceptance Criteria:
Text updates render without manually refreshing.
Dragging updates the canvas.
Image replacement updates the canvas.
Preview reflects hidden and visible layers.
Output dimensions remain consistent with the selected template.
The application must not distort the poster merely to fit the browser window.
FR-09 — Export
Requirement: Users can download completed designs to their computer.
Required Formats:
PNG.
JPG.
Acceptance Criteria:
Export uses the template's original pixel dimensions by default.
No editor selection boxes or controls appear.
No watermark is added.
Fonts and images are loaded before output is generated.
Hidden elements do not appear.
Export works after text and image edits.
Browser initiates a local download.
Recommended filename pattern:
arnifi-project-name-1080x1350.png
The browser determines whether the file saves directly to Downloads or prompts the user, depending on their settings.
FR-10 — Project Persistence
Requirement: Users should not lose progress during a stakeholder demonstration.
Acceptance Criteria:
Project state is saved locally.
Refreshing restores the latest saved changes.
A project can be reopened.
Imported images remain available after a refresh.
A storage failure produces a visible message.
No user accounts or cloud project database are required for MVP.

12.1 Why React + TypeScript?
Suitable for an interactive web application.
Component-based architecture.
Strong support for reusable UI.
TypeScript improves maintainability of layered template data.
Works well with a pre-existing design system.
12.2 Why Fabric.js?
The canvas editor needs to support:
Selectable objects.
Draggable elements.
Resizing and transforms.
Text objects.
Image objects.
Layer stacking.
Serialization.
Image export.
Fabric.js provides core capabilities for these interactions.
Do not build a canvas engine from scratch.
Use a React wrapper/component architecture that keeps the Fabric canvas instance stable rather than recreating it on every React render.
12.3 Why Vite?
This MVP does not require server-side rendering or a complicated backend.
Vite supports a lightweight frontend build that can be deployed as a static web application.
12.4 Why Local-First Storage?
The initial application is intended for a stakeholder demonstration.
Storing project state locally avoids unnecessary authentication, database setup, and cloud infrastructure.
Use IndexedDB for project data and uploaded assets.
Note that local projects are specific to the browser/device. Cross-device synchronization is not part of this MVP.
12.5 Deployment
The application should:
Work locally during development.
Build successfully for production.
Be deployable to a shareable URL.
Include seeded templates and project assets.
Load without Figma access at runtime.
Never expose Figma access tokens or other credentials in frontend code.

Editing must not unexpectedly change:
Text hierarchy.
Original image crop.
Spacing.
Logo placement.
Background.
Aspect ratio.
Changes should happen only through user interaction.
14.4 Content Overflow
Marketing users may paste content that is longer than the original copy.
The tool should:
Detect overflow.
Show a clear warning.
Allow text box resizing or font adjustment.
Avoid silently deleting or clipping content.
Do not introduce unrequested AI rewriting as a workaround.
14.5 Responsive Application
The web app is desktop-first because precise poster editing requires screen space.
Support common desktop and laptop widths.
For smaller screens, prioritize readable navigation and show a clear desktop recommendation if full editing cannot be used comfortably.
The poster's original output dimensions must remain independent of the editor's responsive layout.

15. Design Fidelity and Quality Standards

Correct aspect ratio.
Correct typography.
Accurate image placement.
Original color hierarchy.
Brand elements.
Relative spacing and alignment.
15.2 Validation Process

Compare them at matching dimensions.
Identify visible differences.
Correct significant mismatches.
Test text and image editing.
Test exporting.
Mark the template as validated.

15.3 Quality Gates
Gate A — Import
The template renders without missing required layers.
Gate B — Visual
No significant unexplained differences from the source reference.
Gate C — Editing
Text and image editing work correctly.
Gate D — Export
The downloaded image matches the edited design.
All 20 templates should pass the functional gates before being described as complete.
At least 3–5 representative templates should receive especially thorough visual review for the stakeholder demonstration.

Save authorized assets within the application

24. Explicit Instructions for Claude Code

Mandatory Working Rules
Rule 1 — Inspect before implementing
Inspect the existing repository, design system, Figma MCP access, and available Figma source before making architectural decisions.
Rule 2 — Reuse the existing design system
The Arnifi design system has already been supplied. Do not create a competing design language or arbitrarily replace its components, tokens, fonts, or conventions.

The product owner is a designer without technical coding experience.
